# 中文发布素材

## 主标题

我做了一个不依赖向量数据库的本地知识库：BM25 + Jev 重排实测

## 掘金摘要

不建向量数据库，本地知识库能做到什么程度？我用完整 BEIR NFCorpus 测试集对比了 BM25、Jev 重排、Agentic 多关键词检索和可选混合检索。结果显示，BM25 Top 30 加 Jev 后 nDCG@10 相对提升 15.57%；Agentic 关键词检索 + Jev 达到 0.430969，与本次最佳的混合检索 + Jev 相差 3.01%。本文记录架构、成本、延迟、分块选择和开发踩坑。

## 知乎开场

先给结论：不使用向量数据库，完全可以做出一套有竞争力的本地知识检索；但这不代表 Embedding 没有价值，也不代表系统完全离线。

我把 BM25、Agentic 关键词扩展、Embedding 混合召回和 Jev 重排放到同一套 3,633 文档、323 问题的公开测试集上。无向量的 Agentic + Jev 得到 0.430969 nDCG@10，本次最好的混合检索 + Jev 是 0.444327。真正有用的不是宣布哪条路线“胜利”，而是知道每一层到底增加了多少质量、延迟、成本和隐私边界。

## 微信公众号导语

做知识库一定要先上向量数据库吗？我做了一套更简单的路径：本地 SQLite BM25 负责召回，Jev 负责判断候选证据是否真正相关，最后再让大模型根据证据生成带引用的回答。为了验证它不是只能回答几个手写问题，我在完整 BEIR NFCorpus 测试集上对比了七条检索链路。结果既证明了无向量方案的上限，也说明了 Embedding 什么时候仍然值得加入。
