# Jev RAG 七种玩法全测：从 BM25 重排到 Agentic Hybrid，哪条路线真正有效？

过去两天，我把 Jev RAG 从一条简单的 `BM25 → Jev → 大模型回答` 流程，扩展成了七种可以直接切换的检索路径。

这些路径里，有完全不需要向量的，有把关键词检索和 Embedding 融合的，有让 Agent 规划多轮搜索词的，也有绕开 BM25、直接让 Jev 逐层搜索全部文段的。除此之外，我还测试了知识分类树、统一 Passage Gate，以及在 Jev 排序后重新加入原始召回排名的做法。

但“玩法更多”本身没有意义。真正需要回答的是：

1. 哪一种组合真正提高了检索质量？
2. 提升来自召回、Jev 重排，还是最后的排名融合？
3. 哪些看起来更智能的设计，实际反而降低了效果？
4. 如果要做本地知识库，应该选择哪一条路线？

为了尽量把这些问题说清楚，本文所有主要数字都来自同一套公开测试：BEIR NFCorpus 完整测试集，共 3,633 篇文档、323 个查询。所有方案使用相同语料、查询、相关性标注和指标实现。

费用均指对应完整实验中记录的供应商费用，不是单次查询价格。延迟数据来自不同阶段的冷跑、试跑或缓存恢复记录，只适合判断量级和工程取舍，不能当作严格的同机性能排行榜；实际结果还会随网络和供应商状态变化。

先说结论：

> Jev 能显著改善候选文段的前排顺序，但它不能救回根本没有被召回的文档。当前效果最好的路线不是“只相信 Jev”，而是先尽可能提高候选召回，再把 Jev 排名与原始召回排名做一次轻量融合。

## 一、Jev RAG 现在有哪七种玩法？

七条路径并不是七套互不相关的系统，而是围绕三个阶段做不同组合：

```text
候选召回 → Jev 判断 → 最终排名与回答
```

| 模式 | 第一阶段 | Jev 的作用 | 是否需要向量 | 主要目标 |
| --- | --- | --- | --- | --- |
| BM25 + Jev | SQLite FTS5/BM25 | 对候选逐段判断相关性 | 否 | 最低基础设施、最快接入 |
| Agentic Search + Jev | 两轮搜索词规划 + 多路 BM25 + RRF | 重排扩展后的候选池 | 否 | 不建向量索引也改善同义词召回 |
| Hybrid + Jev | BM25 + Embedding + RRF | 重排词法与语义融合候选 | 是 | 质量、速度和稳定性的平衡 |
| Agentic Hybrid + Jev | 两轮 Agentic BM25 + Embedding + 加权 RRF | 重排后再融合原召回排名 | 是 | 当前最高的整体检索质量 |
| Taxonomy + Hybrid + Jev | 两层语料分类树路由 + Hybrid 扩展 | 重排最多 70 个候选 | 是 | 用知识结构补充候选召回 |
| Hybrid + Passage Gate | Hybrid 候选池 | 同时判断相关、证据、矛盾、提示注入 | 是 | 安全与证据路由实验 |
| Two-level Line Search | Jev 分窗口 Choice，再做全局 Choice | Jev 本身就是搜索器 | 否 | 绕开 BM25 和 Embedding 的全量深搜 |

这七种方式可以进一步分成三类：

- **召回优先**：BM25、Agentic、Hybrid、Agentic Hybrid、Taxonomy；
- **判断优先**：普通 Jev 重排、统一 Passage Gate；
- **Jev 直接检索**：两级 Line Search。

## 二、同一套数据下，结果到底怎么样？

下面是完整 NFCorpus 测试中最有代表性的结果：

| 方案 | nDCG@10 | MRR@10 | Recall@10 |
| --- | ---: | ---: | ---: |
| BM25 Top 30 | 0.305654 | 0.512697 | 0.147309 |
| BM25 Top 30 + Jev | 0.353235 | 0.585817 | 0.158667 |
| BM25 Top 50 + Jev | 0.362468 | 0.593023 | 0.164474 |
| Two-level Jev Line Search | 0.366280 | **0.657660** | 0.169397 |
| Hybrid + Unified Passage Gate | 0.376298 | 0.618043 | 0.166977 |
| Agentic Lexical Top 50 | 0.380168 | 0.597940 | 0.185464 |
| BM25 + Embedding RRF Top 50 | 0.396712 | 0.632089 | 0.193977 |
| Multi-round Agentic Hybrid Top 50 | 0.424145 | 0.637722 | 0.206303 |
| Agentic Lexical Top 50 + Jev | 0.430969 | 0.644041 | 0.204138 |
| Hybrid Top 50 + Jev | 0.444327 | **0.654583** | 0.214907 |
| **Agentic Hybrid + Jev/原召回排名融合** | **0.450750** | 0.652606 | **0.220885** |

如果只看最终数字，Agentic Hybrid 是当前第一。但真正有意思的不是这张排名表，而是每增加一层以后，指标为什么会变。

## 三、玩法一：BM25 + Jev——最简单，但绝不是没效果

默认路线只需要 SQLite：

```text
本地文档 → FTS5/BM25 Top 30 → Jev 重排 → 回答模型
```

BM25 Top 30 的 nDCG@10 是 `0.305654`。加入 Jev 后提高到 `0.353235`，相对提升 `15.57%`；MRR@10 从 `0.512697` 提高到 `0.585817`。

这说明 Jev 很适合做第二阶段判断：候选已经找出来以后，它能把真正包含证据的文段向前移动。

但 Recall@30 完全没有变化，仍然是 `0.189025`。原因非常直接：Jev 只能重排这 30 个候选，不能把第 31 名以后的相关文档凭空找回来。

我还把候选池从 30 扩大到 50。nDCG@10 从 `0.353235` 提高到 `0.362468`，但中位延迟从约 `1.08 秒` 增加到 `1.92 秒`，本次完整测试观察到的 Jev 费用从约 `$0.164` 增加到 `$0.261`。

所以默认 Top 30 不是因为 30 是某个神奇数字，而是它在这套数据上提供了更好的质量、延迟和费用平衡。

**适合场景：**文档里有明确产品名、编号、API 名称、术语或中文关键词；希望部署简单，不想维护 Embedding 索引。

## 四、玩法二：Agentic Search + Jev——不用向量，也能补词汇召回

BM25 最大的问题不是速度，而是用户和文档可能没有使用同一组词。

Agentic 模式没有让大模型直接搜索文件。它只负责规划本地搜索词：第一轮根据问题生成五条查询，第二轮阅读少量第一轮标题和摘要，再生成五条补充查询。所有查询仍然在本地 SQLite BM25 上执行，最后用 RRF 合并前 50 个候选。

```text
用户问题
  → 第一轮五条关键词查询
  → 本地 BM25
  → 查看少量标题/摘要
  → 第二轮五条查询
  → 多路 BM25 + RRF
  → Jev 重排
```

只看召回阶段，Agentic Lexical 的 nDCG@10 已经达到 `0.380168`，Recall@50 从普通 BM25 的 `0.209810` 提高到 `0.280765`。再加 Jev 后，nDCG@10 达到 `0.430969`。

相对 BM25 Top 50 + Jev，这是一项 `18.90%` 的提升。它距离 Hybrid + Jev 的 `0.444327` 只差 `0.013358`，但配对 Bootstrap 区间仍然偏向 Hybrid，因此不能宣称二者已经等价。

代价也很明确：两轮规划增加了模型调用。完整测试中，规划和 Jev 合计观察费用约 `$0.476`；估算串行在线中位延迟约 `7.52 秒`。

**适合场景：**不愿建立向量索引，但查询经常出现同义词、缩写、口语表达或跨语言叫法；能够接受额外规划延迟。

## 五、玩法三：Hybrid + Jev——当前最稳妥的高质量路线

Hybrid 同时保留关键词精确命中和 Embedding 语义召回：

```text
BM25 Top 50 ─┐
             ├→ RRF Top 50 → Jev 重排
Embedding 50 ┘
```

只做 BM25 + Embedding 融合，nDCG@10 就从 BM25 的 `0.305654` 提高到 `0.396712`，Recall@50 从 `0.209810` 提高到 `0.318075`。

再加 Jev 后，nDCG@10 达到 `0.444327`。相对 BM25 Top 50 + Jev 的 `0.362468`，提升 `22.58%`。

这个结果说明了一件非常重要的事：

> Jev 重排很重要，但高质量候选池更重要。Embedding 首先把 BM25 漏掉的相关文档带回来，Jev 才有机会把它们推到前排。

本次 3,633 篇文档的 Embedding 索引一次性构建约 285 秒，观察费用约 `$0.162`，之后缓存在本地。完整 Jev 阶段观察费用约 `$0.368`。十查询冷启动端到端试跑的中位延迟约 `3.17 秒`。

**适合场景：**希望得到稳定的高质量结果，能够接受一次性 Embedding 建索引和查询时的远程向量调用。

## 六、玩法四：Agentic Hybrid——目前最高分，但提升来自最后一步

今天新增的 Agentic Hybrid 把两条召回支路放在一起：

```text
两轮 Agentic 关键词规划 → 多路 BM25 ─┐
                                     ├→ 加权 RRF Top 50 → Jev
原始问题 Embedding ──────────────────┘
                                              ↓
                                  Jev 排名 + 原召回排名融合
```

Agentic 分支和向量分支的权重在开发集上选定为 `0.65:1.0`。融合后的候选池 Recall@50 达到 `0.333047`，高于普通 Hybrid 的 `0.318075`；召回阶段 nDCG@10 为 `0.424145`。

但第一次看 Jev 结果时，提升并没有想象中大：

- Hybrid + Jev：`0.444327`；
- Agentic Hybrid + Jev：`0.445761`。

二者只差 `0.001434`，配对 Bootstrap 区间跨过零，因此不能证明 Agentic Hybrid 的 Jev 排序显著优于普通 Hybrid。

真正把结果推到 `0.450750` 的，是 Jev 之后的一次本地排名融合：

```text
最终分数 = Jev 排名权重 1.0 + 原召回排名权重 0.25
```

这一步不增加任何模型调用、Token 或供应商费用，却比只用 Jev 排名提高 `0.004989` nDCG@10；其 20,000 次配对 Bootstrap 区间为 `[0.000397, 0.009757]`。

这揭示了一个很值得继续研究的方向：Jev 判断很强，但原召回顺序并不是应该被完全丢弃的噪声。两种排序信号保留了一部分互补信息。

代价是两轮规划仍然慢。冷跑召回阶段中位延迟约 `6.99 秒`，P95 约 `24.39 秒`；规划与 Jev 合计观察费用约 `$0.537`，不含已经缓存的一次性语料 Embedding 成本。

**适合场景：**质量优先、问题复杂、可以容忍数秒级规划时间；不适合作为所有简单问答的默认路径。

## 七、玩法五：Taxonomy——候选召回提高了，最终排序却没有提高

Taxonomy 模式先用语料 Embedding 构建两层知识分类树。查询时选择四个叶子节点，在原 Hybrid Top 50 后最多补充 20 个不同候选，再交给普通 Jev 重排。

它确实完成了召回目标：

- Hybrid Recall@50：`0.318075`；
- Taxonomy 扩展 Recall@70：`0.342964`；
- 121 个查询获得了原候选池里没有的相关文档。

但最终 nDCG@10 是 `0.441851`，略低于 Hybrid + Jev 的 `0.444327`。

原因很可能不是分类树没有找到新文档，而是候选池从 50 增加到平均 67.76 后，排序问题也变难了。更多候选提高了理论上限，同时也增加了相似噪声和 Jev 的判断负担。

这条实验提醒我们：

> 候选 Recall 提高是必要条件，但不是最终指标自动提高的充分条件。

**适合场景：**文档天然具有清晰领域层级，需要做分区路由或可解释导航；目前仍属于实验路线。

## 八、玩法六：Unified Passage Gate——功能更丰富，但固定阈值过度过滤

普通 Jev 重排主要回答“这段和问题是否相关”。Passage Gate 一次为每个候选提出四个独立判断：

1. 是否相关；
2. 是否包含可以回答问题的证据；
3. 是否与问题中的事实前提矛盾；
4. 是否包含提示注入风险。

应用代码再根据固定阈值把文段路由到 `include`、`conflicting evidence` 或 `exclude`。

从系统设计角度看，它比单纯重排更接近生产环境中的证据治理。但在 NFCorpus 上，它是一个明确的负结果：16,150 个候选中有 13,631 个被排除，排除率达到 `84.4%`，平均每个查询只保留约 7.8 段。

最终 nDCG@10 为 `0.376298`：

- 低于不使用 Jev Gate 的裸 Hybrid：`0.396712`；
- 更低于普通 Hybrid + Jev：`0.444327`。

问题不是四个判断没有价值，而是固定阈值把“安全过滤”和“检索排序”压成了同一个目标。在一个强调多相关文档召回的评测中，过度排除会直接伤害 Recall 和 nDCG。

**适合场景：**需要提示注入筛查、矛盾证据分流、严格证据门控的系统。阈值应该针对业务数据校准，不能直接把当前固定配置当成通用最优值。

## 九、玩法七：Two-level Jev Line Search——Jev 直接搜全库

Line Search 完全不使用 BM25 和 Embedding。它把全部文段分成最多 255 条的窗口，每个窗口让 Jev `Choice + Noul` 选出若干优胜文段，最后再对所有窗口优胜者执行一次全局 Choice。

```text
全部文段
  → 15 个并行窗口
  → 每个窗口保留 4 个优胜者
  → 60 个全局候选
  → Jev 再做一次 Choice
```

它最亮眼的是首条命中：nDCG@1 达到 `0.554180`，MRR@10 达到 `0.657660`，都是非常强的结果。这说明分层 Choice 很擅长挑出一个最可能的答案。

但 nDCG@10 只有 `0.366280`，Recall@10 为 `0.169397`。它更像“从全库里选一个最佳答案”，而不是稳定地产生一组有良好等级顺序的相关文档。

更大的问题是成本。完整冷跑进行了 5,168 次请求，输入约 1.08 亿 Token，观察费用约 `$4.553`；十查询冷启动试跑中位延迟约 `11.74 秒`，P95 约 `35.75 秒`。

**适合场景：**语料规模较小、单次问题价值高、目标是找到一个最佳答案，或者需要验证一种完全不同于传统召回器的深度搜索路径。它不适合作为普通本地知识库的默认模式。

## 十、把七种玩法放在一起，能得到哪些更一般的结论？

### 1. Jev 是判断层，不是召回魔法

BM25 加 Jev 能把 nDCG@10 提高 15.57%，但候选池 Recall 不会变化。只要相关文档没有进入候选池，再强的重排器也没有材料可排。

### 2. 先提高候选 Recall，再讨论重排

Agentic、Embedding Hybrid 和 Taxonomy 的共同目标，都是把 BM25 漏掉的文档带回来。Agentic 和 Hybrid 最终成功，是因为候选池的覆盖率明显提高；Taxonomy 没有提高最终 nDCG，则说明新增候选还需要更好的排序策略配合。

### 3. 判断维度更多，不代表排序一定更好

Passage Gate 同时回答四个问题，却因为固定阈值过度过滤而落后。生产安全目标、证据门控目标与通用检索指标不是同一个目标，不能只用一个分数评价所有价值。

### 4. 原始召回顺序值得保留

Agentic Hybrid 的最佳结果来自 `Jev 排名 + 原召回排名` 的本地融合。Jev 提供语义证据判断，BM25、Embedding 和 RRF 提供检索先验；二者不是非此即彼。

### 5. “无向量”是一种部署选择，不是一种信仰

Agentic + Jev 在不建立向量索引的情况下达到 `0.430969`，已经是很强的结果。但当前测试仍由 Hybrid 与 Agentic Hybrid 领先。是否使用 Embedding，应该由数据更新频率、隐私边界、延迟预算和检索质量共同决定。

## 十一、实际项目应该怎么选？

| 你的优先级 | 推荐模式 | 理由 |
| --- | --- | --- |
| 最简单、最低基础设施 | BM25 + Jev | SQLite 即可，效果和成本容易理解 |
| 不建向量但需要更强召回 | Agentic Search + Jev | 用多轮词法搜索解决词汇失配 |
| 综合质量与延迟 | Hybrid + Jev | 当前最稳妥的高质量方案 |
| 质量优先、复杂问题 | Agentic Hybrid | 当前最高 nDCG@10，但规划延迟较高 |
| 有清晰知识层级 | Taxonomy | 可提高候选覆盖，仍需继续优化排序 |
| 安全、矛盾和证据治理 | Passage Gate | 适合业务阈值校准，不宜照搬固定阈值 |
| 小库、高价值深搜 | Line Search | 首条命中强，但成本和延迟最高 |

我的默认建议仍然是：

1. 先从 BM25 + Jev 开始，建立一个可解释的基线；
2. 如果失败来自同义词和表达差异，尝试 Agentic Search；
3. 如果质量仍不够，再启用 Embedding Hybrid；
4. 只有在复杂问题确实值得更高延迟时，才切换 Agentic Hybrid；
5. Passage Gate、Taxonomy 和 Line Search 应该视为针对特定目标的实验模块，而不是越多越好的“高级功能”。

## 十二、最后：Jev RAG 的“新范式”到底是什么？

Jev RAG 真正值得讨论的，不是“用 Jev 替代向量数据库”，也不是“关键词检索战胜 Embedding”。

更准确的说法是：

> 把知识检索拆成召回、判断、策略和生成四层，让每一层都可以独立替换、测量和组合。

- BM25、Embedding、Agentic 和 Taxonomy 负责把候选找回来；
- Jev 负责对有限候选做快速、类型化的证据判断；
- 应用代码负责阈值、排序融合、缓存和安全边界；
- 回答模型只负责基于最终证据组织语言。

这套拆分允许我们看到失败究竟发生在哪里：是搜索词没覆盖、Embedding 没召回、Jev 排错、阈值过严，还是回答模型没有正确使用证据。

七种玩法的价值不在于给界面增加七个选项，而在于它们把同一套问题的七种工程取舍放到了可以复现、可以比较的位置上。
